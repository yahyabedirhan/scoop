# 04 - Icon Redesign

Status: in progress, second prototype round
Last updated: 2026-10-03

Builds on the ice-cream-scoop icon from 0.0.6 (`feat: draw an ice-cream-scoop
icon`). Covers only the icon, the README header, and the `ON` badge colour.
The inspect lifecycle and copy modes do not change.

## Problem Statement

Scoop's icon looks like a sticker. A violet scoop holds a smiling strawberry
ball with a heavy dark outline, and it reads as playful clip art next to the
other extensions in the toolbar. The maintainer's other project, Shipyard, has
an icon that looks professional, a flat cream figure on a soft khaki-green
tile, and Scoop has nothing comparable. Scoop's README also opens with a bare
`# Scoop` heading, where Shipyard's opens with its logo.

## Solution

Scoop gets a new icon in Shipyard's format. It is one flat figure on a squircle
tile with a soft vertical gradient and a light sheen. The tile is pistachio, a
hue shift of Shipyard's khaki at the same lightness and chroma, so the two
projects look related without being twins. The figure is a scoop of pistachio
ice cream between two angle brackets, `<●>`. It reads as an HTML element and as
ice cream at once. The brackets and drip are cream, and the ball is a light
pistachio tint.

The README opens with the logo centred at 128 px above a centred title, the way
Shipyard's does. The toolbar's `ON` badge moves from Chrome blue to a deep
pistachio so it belongs to the same palette.

Two runner-up icons are kept as alternates until the maintainer decides at PR
review whether they stay. They are the ball with a mouse pointer and the
plain ball.

## User Stories

1. As a Scoop user, I want a toolbar icon that looks as polished as the other extensions I have pinned, so that Scoop does not look like a toy.
2. As a Scoop user, I want the icon to read clearly at 16 px on a light toolbar, so that I can find it at a glance.
3. As a Scoop user, I want the icon to read clearly at 16 px on a dark toolbar, so that it works in dark mode too.
4. As a Scoop user on a high-density screen, I want the 32 px icon to be sharp, so that the toolbar icon is not blurry.
5. As a Scoop user, I want the 48 px icon on `chrome://extensions` to show the full drawing, so that the extension is recognizable in the extension list.
6. As a Scoop user, I want the icon to suggest both "web element" and "ice-cream scoop", so that the name and the purpose connect.
7. As a Scoop user, I want the `ON` badge to stay readable on top of the new icon, so that I can still tell when inspect mode is on.
8. As a Scoop user, I want the `ON` badge in a colour that matches the icon, so that the extension looks like one designed thing.
9. As the maintainer, I want Scoop's icon to look like a sibling of Shipyard's, so that my projects share a visual identity.
10. As the maintainer, I want Scoop's tile colour distinct from Shipyard's khaki, so that the two are never mistaken for each other.
11. As the maintainer, I want the README on GitHub to open with the logo and a centred title, so that the repo page looks like Shipyard's.
12. As the maintainer, I want the README logo sharp on retina screens, so that it is drawn from a larger image than the 128 px toolbar icon.
13. As the maintainer, I want the README logo to have descriptive alt text, so that screen-reader users know what it shows.
14. As the maintainer, I want the README logo to look right on GitHub's light and dark themes, so that neither theme shows a broken or invisible logo.
15. As the maintainer, I want the runner-up icons kept as previews until I decide, so that I can switch or drop them at review without redrawing.
16. As the maintainer, I want to switch which variant is the shipped icon with one generator option, so that changing my mind is cheap.
17. As the maintainer, I want every icon still generated by one standard-library Python script, so that `npm run gen-icons` keeps working with no new dependency.
18. As the maintainer, I want the generator's output to be identical on every run, so that regenerating never produces a spurious diff.
19. As the maintainer, I want the 16 px icon drawn as a simpler silhouette than the large sizes, so that small sizes are not muddy.
20. As the maintainer, I want a test that every icon in the manifest exists at its declared size, so that a broken regeneration is caught before release.
21. As the maintainer, I want the release recorded as 0.0.7 in the changelog, so that the icon change has a version.
22. As a contributor, I want the README's development table and the design doc to describe the new icon, so that the docs match what ships.
23. As a contributor, I want the prototype that chose the icon kept on its own branch, so that I can see what was compared and why.

## Implementation Decisions

- **Generator.** `tools/gen-icons.py` stays standard-library Python, with signed
  distance functions and supersampling. Its geometry and palette are replaced.
  It draws the tile and the figure, which it currently does not. It writes the
  four extension icons (16, 32, 48, 128), a 512 px README logo, and 512 px
  previews of the alternates. Output is deterministic.
- **Variants.** The generator knows three figures, `brackets` (the shipped
  icon), `pointer` and `ball`. One option names which variant is written as the
  extension icons and README logo, defaulting to `brackets`. The other two are
  written only as previews. The previews live beside the README logo, not in
  `icons/`, because the build copies `icons/` into `dist/` whole and the
  alternates must not ship in the extension.
- **README logo.** A 512 px PNG of the shipped variant in the same folder
  layout Shipyard uses (`assets/images/logo/`), embedded at width 128.
- **Tile.** A squircle (superellipse, n = 5) with a vertical gradient and a
  white sheen over the top half fading to nothing at the middle (14% opacity at
  the top), all as Shipyard's logo does. The 48 and 128 px icons keep Chrome's
  recommended transparent margin around the tile (about 12.5% at 128 and 6% at
  48). The 16 and 32 px tiles fill the canvas.
- **Palette.** These colours come from the prototype, which shifted Shipyard's
  khaki (`#809741` → `#637532`) to hue 140 in OKLCH, with lightness +0.02 and
  chroma × 0.95. The tile runs from `#6da361` at the top to `#557f4b` at the
  bottom (a straight sRGB blend, about `#619156` at the middle). The figure is
  cream `#FBF6EA`, Shipyard's figure colour, and the ball is `#ceebc8`. The
  `ON` badge is `#37692c`.
- **Figure size.** The figure spans about 76% of the tile at 32 px and up, and
  10% more at 16 px, matching Shipyard's habit of enlarging the small figure.
- **Small sizes.** Below 32 px the figure drops its details (the ball's shine)
  and keeps only the silhouette.
- **Separation.** Where a figure part overlaps another (for example the
  pointer over the ball), a gap in the tile's own colour separates them. The
  figure has no outline.
- **Shipped figure geometry**, from the prototype, in a 100 × 100 figure box
  that is then scaled onto the tile:

  ```text
  brackets  stroke cream, width 10, round caps and joins
            "<" (27,30) → (10,50) → (27,70)
            ">" (73,30) → (90,50) → (73,70)
  ball      circle centre (50,46), radius 19, tint
  drip      segment (56,60) → (56,72), width 8, round caps, tint
  shine     circle centre (43,39), radius 3.5, tile colour at 35%, 32 px and up only
  ```

  The `pointer` and `ball` alternates are drawn on the prototype branch,
  `prototype/icon-redesign`, and are ported from there.
- **Badge.** The background service worker's badge colour constant changes to
  the deep pistachio. The badge text and behaviour do not change.
- **README.** The `# Scoop` heading becomes a centred logo image and a centred
  `<h1>`, as in Shipyard's README. The alt text describes the figure and tile.
  The development table's `gen-icons` row describes the new icon and its
  outputs. A short note lists the alternates and how to switch the shipped
  variant. TODO: drop that note and the alternates if the maintainer rejects
  them at review.
- **Docs and release.** The design doc's mentions of the icon are updated.
  The release is `0.0.7`, with the version bumped wherever it is recorded
  (manifest, `package.json`, lockfile) and a changelog entry.

## Testing Decisions

- A good test checks what ships, not how the generator draws it. The seam is
  the committed icon files as the manifest declares them.
- **New suite in Vitest.** For every size the manifest lists under `icons` and
  under the action's `default_icon`, the file exists, is a PNG, and its header
  states the declared width and height. The 16 px icon's pixel at the middle
  of its left edge is opaque, so the tile fills the canvas at small sizes. The README logo
  exists at 512 × 512. Parsing a PNG header needs no dependency. The width and
  height are fixed offsets in the `IHDR` chunk. Prior art for file-based
  checks does not exist yet, so this follows the existing suites' style
  (`test/*.test.ts`, one `describe` per subject).
- **Determinism.** Running `npm run gen-icons` on a clean checkout leaves
  `git status` clean. This is a manual acceptance step, not a test, because
  the suite does not run Python.
- **Badge.** Covered by `npm run typecheck`. There is no background-worker
  test suite, and adding one for a constant is not worth it.
- **Browser check.** Loading the built extension and looking at the toolbar
  is manual and cannot be verified from an agent session. Say so rather than
  claiming it happened.
- `npm run typecheck` and `npm test` pass before the work is called done.

## Out of Scope

- The inspector's blue highlight box, the floating label, the toast, and any
  other in-page colour.
- A Chrome Web Store listing, promo tiles, or screenshots.
- A favicon or any icon for `demo.html`.
- Dark-mode-specific icon variants. Chrome does not swap extension icons by
  theme, and the tile works on both.
- Changing Shipyard's icon or sharing drawing code with Shipyard.

## Further Notes

- The prototype that settled this direction is on the `prototype/icon-redesign`
  branch as `tools/icon-prototype.html`. Open it in Chrome to compare all ten
  motifs, nine palettes, three figure colourings, three body styles and three
  badge colours. Each rejected motif failed for its own reason. The original
  scoop tool reads as a magnifier on a tile, the side-view disher as a ladle,
  the curl as a snail, the double scoop as a figurine, and the selection-bracket
  motif turns to mush at 16 px. Mint was rejected by the maintainer, and pistachio was chosen.
- The maintainer will give feedback on the icon after seeing it. Swapping the
  shipped variant should be a one-option change in the generator.

## Revision after PR review

Added 2026-10-03, after the maintainer looked at PR #15. It overrides the
sections above where they disagree.

- **Feedback.** The pistachio palette is liked and stays as it is. The
  `pointer` icon is liked, but its ice cream looks odd, a dome with straight
  sides. The `brackets` and `ball` icons look odd.
- **Shipped icon.** `pointer` becomes the default variant, written as the
  extension icons and the README logo, unchanged in shape. The README alt text
  describes it.
- **Archive.** `brackets` and `ball` leave the generator and the README note.
  Their 512 px PNGs are kept as a record under `assets/images/logo/archive/`,
  which the generator never writes or deletes. Git history keeps their code.
- **Five new prototypes.** Five new figures, each a different take on Scoop's
  name and purpose, built around the idea of a scoop rather than only an
  ice-cream ball. Not every one carries a pointer. They use the same tile,
  palette, cream figure colour and pistachio tint, and the same generator
  rules (separation gaps, no outline, silhouette below 32 px). Each must read
  at 16 px. None repeats a rejected motif from Further Notes or the
  straight-sided dome. Each is a `--variant` choice with a 512 px preview
  beside the README logo, as the alternates were.
- **Delivery.** PR #15 carries all of this. The maintainer picks the final
  icon from the six at review. The release stays `0.0.7`, with its changelog
  entry revised.

## Second revision after PR review

Added 2026-10-03, after the maintainer looked at the six candidates. It
overrides the sections above where they disagree.

- **Feedback.** None of the candidates shows an actual scoop, the tool you
  scoop ice cream with. `pointer` is still the favourite. `clipboard` looks
  nice and meaningful. `cone-cursor`, `bite`, `monogram` and `window-cup` look
  meaningless.
- **Kept.** `pointer` keeps shipping as the default and `clipboard` stays a
  prototype, both unchanged.
- **Archive.** `cone-cursor`, `bite`, `monogram` and `window-cup` leave the
  generator and the README table. Their 512 px PNGs join `brackets` and `ball`
  in `assets/images/logo/archive/`.
- **Five new prototypes, each built around the scoop tool.** `cursor-scoop`
  pairs a mouse pointer with a scoop. `clipboard-scoop` puts a scoop inside a
  clipboard. `scooper`, `scoop-tub` and `scoop-cone` are three takes on a
  scoop with ice cream: the scoop alone holding a ball, the scoop pulling a
  ball out of a tub, and the scoop dropping a ball onto a cone.
- **Known risk.** The first prototype round rejected the scoop tool because a
  round bowl on a straight handle read as a magnifier and a side view read as
  a ladle (Further Notes). The maintainer now asks for the tool explicitly, so
  each figure must answer those failures. The ice cream should sit visibly
  heaped in or on the bowl, and the scoop's own features, such as its thumb
  lever and grip, should set it apart from a magnifier or a ladle.
- **Rules unchanged.** The tile, palette, cream figure colour, pistachio tint,
  separation gaps, no outline and silhouette-only below 32 px all stay, and
  every figure must read at 16 px.
- **Delivery.** PR #15 carries this round too. The maintainer picks from the
  seven candidates, `pointer`, `clipboard` and the five new figures. The
  release stays `0.0.7`.
